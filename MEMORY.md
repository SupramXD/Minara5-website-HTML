## Payments — Yoco Checkout API (replaced PayFast 2026-09-19)
- Checkout is **server-side only** (Yoco requires it; the old browser-side PayFast sandbox fallback with hardcoded merchant credentials is gone). `createYocoCheckout` (callable) POSTs `https://payments.yoco.com/api/checkouts` with `Authorization: Bearer <secret>` + `Idempotency-Key: <reference>`, saves a pending `orders/<EXTRAIT-…>` doc (`paymentGateway: "yoco"`, `stockDeducted:false`) and returns `redirectUrl`; the storefront does `window.location.href = redirectUrl` so the browser keeps `studioextrait.co.za` as the referrer (that is what Yoco matches against a verified domain).
- **Only the webhook may mark an order paid.** `yocoWebhook` (`POST /yocoWebhook`) verifies `webhook-signature` (HMAC-SHA256 of `webhook-id.webhook-timestamp.<rawBody>` with the base64-decoded `whsec_` secret, constant-time compare) → 403 on mismatch; it matches the order via `payload.metadata.orderId` (or `checkoutId`), sets `paid/status/yocoPaymentId/yocoAmountGross/yocoPaymentMethod/yocoCardScheme/yocoCardMask`, then deducts stock once. `success.html` therefore polls `verifyYocoPayment` (15 × 2 s) instead of trusting the browser callback.
- Secrets: `YOCO_TEST_SECRET_KEY` (`sk_test_…`, also the natural home for the live key later) and `YOCO_WEBHOOK_SECRET` (`whsec_…`). Public test key `pk_test_2dff1e63rrv6qKe6af44` lives in `functions/index.js` (`YOCO_PUBLIC_KEY_DEFAULT`, overridable via `YOCO_PUBLIC_KEY`). Changing a secret's *value* = `firebase functions:secrets:set NAME --data-file <file>` → redeploy functions.
- Webhook registered in the Yoco account (test mode): `sub_ngop46lJzpvsXnnuPeVuDnxB` → `https://us-central1-minara5.cloudfunctions.net/yocoWebhook`. A **live** webhook must be registered with the live secret key once live keys unlock (limit 5 webhooks/account, test+live share it).
- Deprecated aliases kept for cached pages: `createPayFastTransaction`, `createPaystackTransaction`, `payfastWebhook`, `paystackWebhook`, `verifyPayFastPayment`, `verifyPaystackPayment` all forward to the Yoco functions — delete them once no cached storefront page calls them.
- Verified end-to-end on deploy (2026-09-19): checkout creation returned `redirectUrl https://c.yoco.com/checkout/…`; a signed probe event returned `200 {"received":true,"matched":true}`; an unsigned one returned `403`; `verifyYocoPayment` returned `verified:true` for the webhook-paid doc and `pending:true` for an unpaid one (probe orders deleted afterwards).

## Payments — Ozow instant EFT + Capitec Pay (added alongside Yoco)
- `checkout.html`'s payment step is **two-step: pick a row, then press one button** (it was tap-to-pay tiles until 2026-10-13). `.payment-methods` is a `role="radiogroup"` of THREE `.payment-tile` buttons ("Pay by card" / "Instant EFT" / "Capitec Pay") stacked as rows with a visible radio dot (`.payment-tile-radio`); every rail is described by the `GATEWAYS` registry (`{label, createFn, selectedBankId}`) and `resolveGateway()` is the only sanitiser, so no ternary spells a gateway name out any more; the old `.payment-divider` rule and the `.payment-tile-go` redirect cues are gone. `window.selectGateway('yoco'|'ozow'|'capitec')` **only selects**: it stores the choice in `window.__extraitGateway`, repaints `.selected` + `aria-checked`, clears `#paymentError` and saves the draft, so a stray tap can never start a payment. The single action is `#payBtn` (`.pay-continue-btn`, lime `#ccff00`, lock icon + arrow, label `#payBtnLabel` = "Continue to Yoco / Continue to Ozow / Continue to Capitec Pay") wired to `window.submitPayment()`, which calls `form.requestSubmit()` so the browser's own required-field validation runs BEFORE anything reaches the gateway (fallback: `checkValidity()` + `handleCheckoutSubmit`, else `reportValidity()`); Enter inside a field goes through `handleFormKeydown` to the same submit. `getSelectedPaymentMethod()` reads `window.__extraitGateway`; `handleCheckoutSubmit` locks both rows **and** `#payBtn` (`setPaymentTilesDisabled`), shows `#payStatus` ("Securing your <Gateway> payment...") and calls `createOzowCheckout` or `createYocoCheckout`. `updatePaymentMethodUI()` relabels `#payBtnLabel` and `#payRedirectNote` ("Secure payment page by <Gateway>.") for the selected gateway. There is no `#gatewayNotice` and no header gateway badge.

- **Checkout draft (`minara_checkout_draft`)** so a cancelled payment never has to be retyped: `window.saveCheckoutDraft()` snapshots every field (name, email, alt email, phone, building, street, suburb, city, province, postal, instructions, delivery date, whether the alt-email row is open, and the chosen gateway) on `input`/`change`, on tile tap, and on `pagehide`/`beforeunload` (the address autocomplete writes `.value` directly so it fires no `input` event). `restoreCheckoutDraft()` + `attachCheckoutDraftAutosave()` run inside the render `setTimeout`, so a customer bounced to `cancel.html` (Ozow sends both cancels *and* errors there) can press "Return to Checkout" and find everything still filled in. `success.html` clears the draft right next to the `minara_cart` clear - keep both calls together.
- `createOzowCheckout` (callable) POSTs `https://api.ozow.com/postpaymentrequest` with `SiteCode`/`ApiKey` **headers** (keys are never in the body/URL) and a `HashCheck` field. Per Ozow's *legacy* spec, the hash is: lowercase every value, concatenate `SiteCode + CountryCode + CurrencyCode + Amount + TransactionReference + BankReference + Optional1..5 + Customer + CancelUrl + ErrorUrl + SuccessUrl + NotifyUrl + IsTest`, **then append the private key**, then SHA512-hex. `selectedBankId` is field 18 - straight after `IsTest`, skipped entirely when the rail does not use one. `timingSafeEqual` is used on verify.
  - `Amount` **must** be `toFixed(2)` — a dropped trailing zero (`1290.0`) is the #1 cause of `HashCheck` failures.
  - `customerCellphoneNumber` is intentionally **not** part of the hash; the phone travels in `Optional2`.
- **Only the webhook may mark an order paid.** `ozowWebhook` (`POST /ozowWebhook`, raw form-urlencoded body, public HTTPS URL) verifies `Hash` over `OZOW_NOTIFICATION_HASH_FIELDS` (`SiteCode, TransactionId, TransactionReference, Amount, Status, Optional1..5, CurrencyCode, IsTest, StatusMessage`) *before* touching Firestore, then matches `TransactionReference` → order, sets `paid`/`ozowTransactionId`/`ozowStatus`/`ozowAmount`, and deducts stock once. **Idempotent**: an `alreadyPaid` order is never downgraded.
  - Ozow returns **HTTP 200 even for rejections** — always key off `errorMessage` / presence of `url`, never off the status code.
  - Paid vs failed status buckets live in `OZOW_PAID_STATUSES` / `OZOW_FAILED_STATUSES`; anything else (Pending/Created/…) stays pending.
- `verifyOzowPayment` (callable) is an alias of `verifyYocoPayment`; `success.html` picks it from `?gateway=ozow` **or** the order doc's `paymentGateway` (Ozow appends its own query fields to Success/Cancel/Error URLs, so the page matches leniently and trusts the order doc). `cancel.html` stays gateway-neutral (Ozow sends both cancels and errors there).
- Required secrets: `OZOW_API_KEY` **is the private key** (hash signing/verification only, never transmitted), `OZOW_API_KEY_NORMAL` is the API key sent in the `ApiKey` header, `OZOW_SITE_CODE` is the site code (`AAA-AAA-AAA`). `OZOW_API_BASE_URL` points at `https://stagingapi.ozow.com` for staging and `OZOW_IS_TEST=true` flips `isTest`.
- Hash fidelity notes (both directions must match Ozow's reference code exactly): payin request hash lowercases the whole `concatenated + privateKey` string, skips unused/empty fields, and hashes the boolean as `true`/`false`; notification verification additionally normalises `Amount` with `Number(x).toFixed(2)` (falling back to the literal string when it is not numeric, never `"NaN"`). The webhook also stores `ozowSubStatus` and `ozowBankName` for reconciliation.
- No Hosting rewrite is used for either webhook — `firebase.json` has no `rewrites` block, so both Yoco and Ozow call the direct `https://us-central1-minara5.cloudfunctions.net/<fn>` URLs. Ozow's notify URL must be publicly reachable over HTTPS.

## Troubleshooting (when the admin shows a sync error)
- **"GitHub sync failed: internal" popup** = the sync Cloud Function did not answer at all. The Firebase JS SDK collapses infrastructure failures (function unreachable / no CORS headers / Cloud Run 5xx) into `FunctionsError("internal", "internal")`, so a bare "internal" is NEVER about the edit itself. Diagnose with `node tools/check-functions-health.js` (probes every HTTP function; healthy = JSON callable body **or** an HTTP 401/403/405/2xx from the endpoint — a callable that validates input answers 400 + `{"error":…}` and is healthy, and `yocoWebhook`/`payfastWebhook` *should* answer 403 to a credential-free probe; `DOWN` = 404/5xx or Google's HTML error page).
- **2026-09-14 outage (verified)**: every function in project `minara5` (`syncToGithub`, `trackCourierGuyOrder`, payment callables…) returned Google Frontend's generic HTML `500 Server Error` with no CORS headers, so admins could still write to Firestore but nothing could sync to GitHub. Firebase Hosting (`studioextrait.co.za`, 200) and Firestore were fine. Cause: the project has **no active billing** — proof: `firebase deploy --only functions --project minara5` fails with `Error: Request to https://secretmanager.googleapis.com/.../secrets/GITHUB_TOKEN had HTTP Error: 403, This API method requires billing to be enabled…`, and Cloud Functions v2 runs on Cloud Run which requires the Blaze plan (hosting-only deploys still succeed). Fix: re-enable billing (Firebase console → Usage and billing → Blaze, or the URL in that error) and `firebase deploy --only functions --project minara5`, then re-run the health check.
- **Which pipeline serves the live site (verified 2026-09-15)**: `studioextrait.co.za` is **Cloudflare → GitHub Pages**, NOT Firebase Hosting (proof: `/firebase.json` and `/functions/index.js` return 200 on the custom domain but 404 on `minara5.web.app`; Pages' default `cache-control: max-age=600`; `x-github-request-id` / Fastly headers; Cloudflare rewrites asset TTLs to `max-age=14400`). Therefore **every push to `main` publishes the live site** - including the commits made by the `syncToGithub` Cloud Function and by `.github/workflows/sync-firestore-products.yml` (both produce `pages build and deployment … success` runs). `firebase deploy --only hosting` only updates `minara5.web.app`. The `.github/workflows/deploy.yml` "Deploy hosting" step fails on every push (missing/invalid `FIREBASE_TOKEN`) but that is cosmetic for customers - fix it only if `minara5.web.app` should track the repo. Because Pages/Cloudflare ignore custom cache headers, cache-busting on the live domain can only be done with versioned URLs (`?v=`, Cloudflare misses on new query strings - verified).
- **Firestore → products.json FALLBACK (works without Cloud Functions)**: `node tools/pull-firestore-to-repo.js` rebuilds `products.json` (and writes any base64 images out to `images/products/*`) straight from the world-readable Firestore `products` collection; `--check` only reports the diff. - **"Unsupported field value: undefined" on a product save (fixed 2026-09-15)**: `openEditModal` used to build customisation blocks with `price: undefined` whenever the Firestore block had no official price, and the Web SDK rejects `undefined` — killing the ENTIRE save (only products WITH customisation blocks were affected; empty-`customisations` products saved fine). - **Image caching (fixed 2026-09-15)**: `firebase.json` gave *every* image `max-age=604800`, so a photo swapped in the admin (same file name, e.g. `images/products/<id>.webp`) stayed stale for days for all visitors and the CDN. Now `images/products/**`, `images/hero/**` and `images/second-hero/**` are served `public, max-age=0, must-revalidate` (cheap 304 revalidation), while static art keeps the long cache. On top of that, admin-editable images get a `?v=<version>` tag from the row's own Firestore `timestamp`: `window.minaraVersionedImage()` + `minaraRegisterImageVersions()` + `minaraDecorateProductImages()` in `header.js` (registered inside `loadLiveProducts()`, applied in the `applyLiveStock` hooks of `home-products.js`/`catalog-grid.js` and in `product-core.js`), and `minaraDecorateHeroImages()` for `home-hero.js` (hero/second-hero settings `timestamp`). The hosting-side headers only apply to `minara5.web.app`; on the custom domain Cloudflare controls TTLs, so the `?v=` versioning is what makes new photos appear immediately (Cloudflare misses on a new query string - verified).
- **JS cache-busting on the live domain (verified 2026-10-05)**: `studioextrait.co.za` serves `header.js` and `js/core/cart.js` with `Cache-Control: max-age=14400` (4 hours) - the `no-cache` rules in `firebase.json` only apply to `minara5.web.app`. So a change to `js/core/*.js` needs the repo's date token bumped in **two** places: the import inside `header.js` (`./js/core/cart.js?v=...`) *and* the `header.js?v=...` reference on every page that loads it (current token `20261015`, 28 references across 15 files: `./js/core/cart.js?v=` inside `header.js` plus `<link rel="modulepreload" href="header.js?v=…">` and `<script type="module" src="header.js?v=…">` on each page that loads it). Bump BOTH. HTML is cheap by comparison (`checkout.html` answers plain `max-age=600` with no Cloudflare caching), so a push shows up in about 10 minutes.
- **Never probe a brand-new `?v=` URL before the origin has rebuilt**: Cloudflare stores whatever it gets under that exact query key for the origin's 4-hour TTL, so one early request pins the OLD body to the NEW token and every visitor gets stale JS. That happened on 2026-10-05 - `js/core/cart.js?v=20261005` was poisoned within seconds of the push, while the identical file with no query, or with `?zz=884411`, already returned the new content (`cf=MISS`). Probe the origin with a throwaway query string instead, and if a token *is* poisoned, bump it once more (current token: `20261015`; on 2026-10-14 the token was bumped twice in one day - a second change to the same file takes the NEXT token, because reusing a token whose body changed pins the old body to it for the whole Cloudflare TTL). **Probe the CUSTOMER domain, not `minara5.web.app`:** on 2026-10-13 `studioextrait.co.za/checkout.html?zz=<throwaway>` served a commit that had been pushed ~3 minutes earlier (it is GitHub Pages - this repo's `CNAME` - behind Cloudflare), while `minara5.web.app` still answered with a build from 2026-09-22, so a stale `minara5.web.app` says nothing about what a customer sees (the Firebase mirror is refreshed separately by `.github/workflows/deploy.yml`).
- **Live verification recipe for a storefront change (used 2026-10-05, cheaper than a browser):** push, wait ~60-90 s for the GitHub Actions hosting deploy, then `Invoke-WebRequest` the page with a throwaway `?probe=…`, `header.js?probe=…` (check the `./js/core/cart.js?v=…` import line it serves) and `js/core/cart.js?probe=…`, and finally the token URLs themselves (first fetch should be `cf=MISS`). Right after a deploy **new static files can 404 for a minute** while the release propagates - re-probe before concluding a file is missing. To *see* a rendering change locally, headless Chrome does it without any dependency: `chrome.exe --headless=new --disable-gpu --hide-scrollbars --allow-file-access-from-files --window-size=720,720 --screenshot=out.png file:///…/mock.html` (build a small mock that copies the real `<style>` block verbatim, then read the PNG back). **Windows gotcha:** `--window-size` is clamped to a ~500px minimum, so a 320px request still lays out at 500px and merely crops the PNG - to test real phone widths put the mock in a 320px `<iframe>` inside a 520px window (the iframe gets a true 320px viewport for media queries) and read numbers back with `--dump-dom` plus a `window.onload` probe that writes element rects into the page.
